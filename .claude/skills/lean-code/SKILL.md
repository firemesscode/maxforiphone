# lean-code — простой код дешевле во всех смыслах

Меньше кода = меньше токенов на генерацию сейчас и меньше токенов на чтение и
правки потом. Лишние абстракции «на будущее» почти всегда оказываются долгом.

## Правила

### 1. Сначала ищи, потом пиши
Прежде чем писать утилиту/хелпер — проверь, нет ли её уже (см. `efficient-search`).
Дублирование — это и лишний вывод, и будущая рассинхронизация.

### 2. Решай задачу, которая поставлена
- Не добавляй фичи, о которых не просили («а вдруг пригодится»).
- Не закладывай конфигурацию/обобщения под несуществующие сценарии.
- YAGNI: понадобится — добавишь тогда, дёшево.

### 3. Минимум абстракций
- Не вводи слой/интерфейс/фабрику ради одного использования.
- Прямой понятный код лучше «гибкого», который читать дороже.
- Три повторения — повод вынести общее; одно-два — ещё нет.

### 4. Без шаблонного шума
- Не пиши комментарии, пересказывающие код (`i++ // увеличиваем i`).
- Комментируй только «почему», когда это неочевидно.
- Не оставляй закомментированный код и заглушки «на потом».

### 5. Используй возможности языка/стандартной библиотеки
Встроенное короче и надёжнее ручных велосипедов (например, методы массивов
вместо ручных циклов там, где это уместно и читаемо).

### 6. Ранний возврат вместо вложенности
Плоский код короче и понятнее глубоко вложенного.

```js
// плохо
function f(u) {
  if (u) {
    if (u.active) {
      return u.name;
    }
  }
  return null;
}

// хорошо
function f(u) {
  if (!u?.active) return null;
  return u.name;
}
```

## Анти-паттерны

- ❌ «Универсальное» решение под один кейс.
- ❌ Копипаста вместо переиспользования.
- ❌ Комментарии, дублирующие код.
- ❌ Спекулятивные параметры/опции, которые никто не вызывает.
- ❌ Новые зависимости ради одной мелкой функции.
